# Conformance

How quint-ts's results are checked against Quint's own tools. The current
results are in [MATRIX.md](MATRIX.md), generated by `bun run conformance`.

## Routes

| Route | What it is | What it can show |
| --- | --- | --- |
| `quint-ts` | This package: Quint's frontend, `src/translate.ts`, tla-ts | The result under test |
| `evaluator-ts`, `evaluator-rust` | `quint run`, Quint's two simulators | Quint's executable semantics on one behavior; on a model, a sample only |
| `official` | `quint verify --backend=tlc`: Apalache's translation, run by the TLC in Apalache's jar | An exhaustive result, through a translation that is under test too |
| `qts/tlc` (graphs only) | quint-ts's translation, run by that same TLC | Separates the translator from the checker |

No route is the authority on its own. A case's expected value comes from
Quint's documentation, cited in the case.

## Operator cases

[operators.ts](operators.ts). Each case is a Boolean expression, checked as
the initial value of `ok` under the invariant `ok`, so every route answers
one question. Its `semantics`:

| Semantics | Meaning | quint-ts must be |
| --- | --- | --- |
| `defined` | The documentation gives the value; the expression is true by it | `passed`, unless the case says why the backend can't check it (`quintTs: "unsupported"`) |
| `undefined` | The documentation says the behavior is undefined | `unsupported` |
| `contested` | Quint's sources disagree on the value | `unsupported` |
| `unspecified` | The documentation doesn't say | `unsupported` |

On a defined case, any other route that doesn't pass is a failure unless the
case's `known` explains that route's outcome. On the others, every route's
outcome is recorded, not judged. The harness also checks that each case's IR
uses the opcodes the case declares.

## Constructs outside the subset

`UNSUPPORTED_CASES` in [operators.ts](operators.ts): each must be refused at
translation.

## Models

[models.ts](models.ts) and [models/](models/). For each model:

1. quint-ts's result must be the expected one.
2. The simulator samples 300 behaviors of 6 steps; a violation it finds
   that quint-ts doesn't is a failure.
3. The full state graph is explored with `-continue` in `qts/tla-ts`,
   `qts/tlc` and `official/tlc`, and the routes are compared as sets: initial
   states, states, transitions (each successor of each state), and the states
   that break the invariant. A route that stops early is incomplete, and an
   incomplete graph never counts as equal.
4. A counterexample from quint-ts must be a path of every graph: it starts in
   an initial state, takes only transitions of the graph, ends in its first
   violating state.

## Results

Each platform's last run is in `results/<platform>-<arch>.json`. CI writes
them for Windows and Linux on every push, as artifacts; the macOS workflow,
started by hand, does the same. `bun conformance/run.ts --report-only
[--from <file>]` rebuilds [MATRIX.md](MATRIX.md) from the results files,
running nothing.

## Limits

- The corpus is small: 30 operator cases, nine models compared as whole
  graphs (two of them on Quint's public `booleans.qnt`), and ten more public
  models that quint-ts can't give a complete verdict on. Records, tuples,
  lists and temporal properties aren't translated, so they aren't compared.
- Quint's simulators can't enumerate a state's successors, so the
  transition relation is compared against TLC's reading of Apalache's
  translation, not against Quint's evaluator.
- States are compared as TLC prints them. Two routes that print one value
  differently would show as a difference, never as a false equality.
- The harness has run on Windows x64, Linux x64 and macOS arm64; see the
  platform table in [MATRIX.md](MATRIX.md) for each one's last commit.
